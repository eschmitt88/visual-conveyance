2 / 11 · What happened

Four hours, seventeen minutes

≈362,000 of ≈1.9 M requests failed — 19.1% average. No data was lost: writes ride a durable queue, and 37,400 delayed webhooks were replayed by 19:05.

Reporting (read replicas) and auth (separate pool) stayed healthy — that capped the peak at 31.2%.

3 / 11 · Cause 1 — the trigger

Trigger · shipped 14:02

One query rewrite abandoned its index

0.4 ms → 24–31 s

per search, before → after the deploy

before · Index Only Scan · p99 2.1 ms → after · Seq Scan · 274 M-row table · ≈312 M rows read then discarded per query

Gloss — index: a sorted lookup structure. The new pattern starts with a wildcard (LIKE '%…%'), which gives it nothing to anchor on; the org filter also left the SQL, so the query ran unscoped.

PR #8841 made search match anywhere in the invoice number. The rewritten query couldn't use its index: every search read all 274 million rows.

Why canary was green: its ~2 M-row table ran the same scan in ~180 ms — under every threshold.

4 / 11 · Cause 2 — first amplifier

Latent since June 22

Two-day-old vacuum debt turned slow into failing

A June 22 backfill left 38.1 M dead tuples — old row versions kept until autovacuum reclaims them. The ≈54.9 M trigger never fired; bloat pushed scans past the 30-second timeout.

A killed query still held its connection for 30 s first.

5 / 11 · Cause 3 — second amplifier

Latent in every client

Jitterless retries pinned the shared pool

4.7×traffic multiplication — 3,200 → 15,020 rpm
1,437peak wait queue (15:58)

Each scan held one of 80 pooled connections for up to 30 s — and clients retried every failure on a fixed 1-second beat, no jitter, no budget. The pool saturated at 15:12.

Every endpoint sharing the pool queued behind the scans.

6 / 11 · How the three causes combined

Remove any one leg and June 24 shrinks

1 · Query regression

Every search becomes a 24–31 s full-table scan.

2 · Vacuum bloat

Scans cross the 30 s timeout — slow becomes failing.

3 · Jitterless retries

Failures retried in phase — traffic ×4.7.

↓

15:12 — the shared pool of 80 exhausts

Every endpoint behind it fails — creation, PDFs, webhooks — and those failures retry too, sustaining the storm until the 17:05 flag-off.

No query change → nothing happens at all No bloat → slow but mostly succeeding; ≈34/80 connections — a one-endpoint degradation No retry storm → near-organic load; the pool holds through the 15:00 job spike

The trigger alone was a one-endpoint problem. Bloat converted slow into failing; retries multiplied failures; the shared pool spread them platform-wide. That is why remediation targets all three legs, not just the trigger.

7 / 11 · Why it took so long to see

68 minutes to the right diagnosis

Alerting watched error rate, not latency — search p99 exploded four minutes before any alert. Dashboards sampled 1 in 100 requests; deploy markers had been broken since June 10.

Blameless: given what responders could see, the network theory was reasonable.

8 / 11 · Why rollback failed — and what worked

Rollback was impossible — the flag wasn't

✕ Roll back the deploy

Migration 0412 had dropped the old covering index; rebuilding it takes ≈6 h. Started 16:05 as insurance — it finished 21:48, after close.

✕ Bump the pool

80 → 200 at 16:20 admitted more concurrent scans and worsened write latency. Reverted 16:31.

✓ Feature flag

invoice_search_contains → 0% at 17:05, after staging verified the exact-match fallback's index. Errors under 3% within ten minutes.

Cleanup: manual VACUUM 17:12–17:50 removed the 38.1 M dead tuples; SLOs met from 17:53; closed 18:19. Contains search returned June 26, fixed and org-scoped.

The release's migration had irreversibly dropped the index the old query needed — rolling back the code would seq-scan just the same. The flag fell back to exact-match search, on an index the migration hadn't touched.
