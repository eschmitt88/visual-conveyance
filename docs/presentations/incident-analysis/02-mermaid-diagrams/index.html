INC-1194 — anatomy of the June 24 ledgerline outage

On 2026-06-24, 14:02–18:19 UTC, ledgerline's invoicing API partially failed for 4 h 17 m — peak 31.2% of requests erroring, 2,312 customer organizations affected, ≈$41,300 in SLA credits — because a deploy-time trigger met two pre-existing latent weaknesses; there was no single root cause.

A leading-wildcard LIKE ("%…%") gives a B-tree index nothing to anchor on — and the rewrite also moved org scoping out of the SQL — so Postgres read the whole table per search, while dead tuples (old row versions an UPDATE leaves behind until autovacuum, a background cleaner, reclaims them) added ≈23 GB, pushing scans past the timeout. Remove any one leg and June 24 shrinks to a one-endpoint degradation: without the bloat, slow searches mostly succeed and the pool holds at ≈34/80; without the retry storm, demand stays near organic levels; without the query change, nothing happens at all.

Detection lag dominated: customers felt latency from 14:07, but the only firing alert watched error rate (14:11), and the correct diagnosis came at 15:19 — 68 minutes later, 50 of them spent actively pursuing the network theory. The blast radius was availability, not integrity: invoice writes ride a durable queue, and every delayed webhook was replayed.

Four systemic gaps — not responder error — made the network theory the most reasonable available explanation; the review is blameless. The flag beat every deploy-pipeline option: rolling back the code would still sequential-scan, because migration 0412 had already dropped the covering index (an index that contains every column the query needs, so the table itself is never touched).

Anatomy of the retry storm

sequenceDiagram
    participant C as Client / SDK
    participant G as API gateway
    participant PB as pgbouncer (pool of 80)
    participant DB as Postgres primary
    C->>G: invoice search
    G->>PB: borrow a pooled connection
    PB->>DB: leading-wildcard LIKE — full-table scan
    Note over PB,DB: connection held up to 30 s per query
    DB--xPB: query_canceled at the 30 s statement timeout
    PB--xG: error
    G--xC: 5xx (504)
    Note over C: retry after a fixed 1 s, 3 attempts, no jitter, no budget
    C->>G: retry waves arrive in phase (1 s oscillation)
    Note over G: inbound 3,200 → 15,020 rpm at peak (4.7×)
    Note over PB: 80/80 busy from 15:12 — client wait queue peaks at 1,437 (15:58)
    Note over G,DB: invoice creation, PDF rendering, webhook dispatch all queue behind 30 s scans

pgbouncer pools connections — requests borrow one of 80 shared server connections instead of opening their own — so 30-second holds starved invoice creation, PDF rendering, and webhook dispatch alike, and the retries queued on the same exhausted pool: extra load, zero extra successes, for nearly two hours (15:12–17:18). The 16:20 pool bump to 200 backfired (more concurrent scans, worse write p99) and was reverted at 16:31 — the 30-second holds were the problem, not the pool size.
