meridian — one pipeline, one SQLite file, everything reads through the store

A self-hosted read-later / RSS service. A one-way ingest pipeline writes articles into a single SQLite database; a small HTTP API, a vanilla-JS web reader, and a CLI read them back out. Two processes (API + workers), no external broker, cache, or database server.

Your first change goes here

  • New source type — a documented 4-file recipe centered on pipeline/sources/.
  • New API endpoint — api/routes.py + api/schemas.py.
  • Almost never in store/ or queue/ — those are stable.

The rules that keep it sane

  • Only store/writer.py writes the database.
  • The extractor is pure: bytes in → Article out, no I/O.
  • Full-text index updated by SQLite triggers only.
  • Nothing imports api/ or cli/.

Tread carefully

  • pipeline/extractor.py — largest file (1,140 LOC), 14 site-specific heuristics, and the codebase's one layering violation.
  • web/js/reader.js — 920 LOC, zero tests; the whole frontend has no test harness.

runtime

How data moves

Flow A — the fetch pipeline (write path)

  1. pipeline/scheduler.py ticks every 60 s, finds feeds whose poll interval (default 30 min) has elapsed, enqueues one fetch job per feed. Typical queue depth 30–60; the health endpoint alerts at 500.
  2. queue/broker.py polls the jobs table every 500 ms and leases jobs to 8 worker threads. Failures retry at 1 min / 5 min / 30 min, then dead-letter.
  3. pipeline/fetcher.py does the HTTP work: conditional GET (ETag / Last-Modified), 20 s timeout, per-host politeness delay.
  4. pipeline/extractor.py turns raw HTML into a structured Article — title, byline, body, word count. Pure, no I/O of any kind · p50 45 ms, p95 320 ms per article.
  5. pipeline/dedup.py computes a 64-bit simhash of the body; Hamming distance ≤ 3 against stored hashes marks a duplicate. About 7% of incoming items are flagged and dropped.
  6. store/writer.py persists each surviving article in a single transaction. SQLite triggers in schema.sql update the articles_fts FTS5 index — application code never writes the index.

End to end, p50 from job dequeue to the article being searchable is 2.1 s, dominated by the network fetch.

Flow B — the read path

GET /articles/{id} hits api/routes.py, reads via store/reader.py, assembles display HTML in render/template.py, then render/annotations.py merges the user's highlights — stored as character offsets into the rendered text — into <mark> spans.

6148

p50 in ms: 6 store read · 14 template · 8 annotations — 28 ms total

The web reader (web/js/reader.js) and the CLI consume the same endpoints; neither has a private backdoor into the database.

discipline

Layering and the five invariants

Import direction is strict and documented in docs/architecture.md: store/ sits at the bottom and imports no other meridian package (stdlib + sqlite3 only); nothing imports api/ or cli/. One known violation exists — and it lives in the scariest file.

allowed import (points at what gets imported) · the violation · HTTP call, not an import

1 · The extractor is pure. Bytes in → Article out. No network, disk, DB, or clock; the same HTML always yields the same Article. Enforced by a property test replaying all 1,400 fixture pages on every CI run.
2 · Only store/writer.py writes the database. Every INSERT, UPDATE, and DELETE in the codebase lives in that one 610-LOC file; everything else reads through store/reader.py.
3 · The FTS index is trigger-maintained. articles_fts is updated only by SQLite triggers in schema.sql; no Python touches it, so it can never drift from the articles table.
4 · Queue jobs are idempotent. Replaying any job must not create duplicate articles — dedup plus the writer's upsert keys guarantee it. This is what makes the retry policy safe.
5 · The API never fetches inline. "Fetch this now" enqueues a job and returns 202 Accepted; only workers touch the network.
The violation, spelled out. pipeline/extractor.py (line 41) imports clean_html() from render/sanitize.py — a sideways pipeline → render edge, present since v0.8. A change to the display sanitizer can silently change what gets stored, and it is why two extractor purity tests are marked xfail. The fix (move clean_html() to a shared location) is tracked as issue #214, top of the debt list.

caution

The three tech-debt hotspots

the scary one

meridian/pipeline/extractor.py

1,140 LOC — largest file in the repo · max cyclomatic complexity 38

Contains 14 site-specific extraction heuristics inlined as if/elif chains, plus the layering violation. Nearly every extraction bug fix lands here, and each one risks changing output for the other 13 heuristics. The 1,400-page fixture corpus is the only safety net.

endpoint pile-up

meridian/api/routes.py

All 31 endpoints in one 830-LOC file · file coverage 54%, below the module's 62%

auth.py exists, but 11 routes inline their own copy-pasted auth check instead of using it. Use auth.py when you add an endpoint.

untested frontend

web/js/reader.js

920 LOC of vanilla JS · zero tests (no JS harness exists)

Highlight anchoring uses character offsets into the rendered HTML, so any markup change in render/template.py silently corrupts existing highlight positions. This coupling caused 3 of the last 10 user-reported bugs.

getting started

Where does your first change go?

Pick what you're adding — each path is a known recipe.

The most common contribution: exactly 4 files

Step-by-step in docs/adding-a-source-type.md. The three existing adapters (rss.py, html_page.py, mailbox.py) each followed this recipe.

  1. meridian/pipeline/sources/base.py — subclass SourceAdapter (implement discover() and fetch_items())
  2. meridian/pipeline/sources/__init__.py — register the class in SOURCE_REGISTRY
  3. meridian/store/migrations/ — one migration extending the source_type CHECK constraint
  4. meridian/cli/commands/add.py — expose the new --type value
Plus a fixture-backed test under tests/unit/pipeline/.

Two files, three if the frontend consumes it

  1. meridian/api/routes.py — the handler (all 31 live here)
  2. meridian/api/schemas.py — request/response dataclasses + validation
  3. web/js/api.js — a fetch() wrapper, if the frontend consumes the endpoint
Use auth.py for the auth check — 11 existing routes inline a copy-pasted version instead, and that's debt, not a pattern to follow. Remember the invariant: endpoints that trigger fetching enqueue a job and return 202 Accepted; they never fetch inline.

One new module

  1. meridian/cli/commands/<name>.py — main.py auto-discovers it
The CLI talks to the API over HTTP via client.py — it never imports backend packages, and your command shouldn't either.
A newcomer's first change almost never touches store/ or queue/. Those layers are stable (91% and 88% covered) and change only with schema migrations.

safety net

Tests: strong backend, absent frontend

412 tests — 348 unit + 64 integration — full suite in ~41 s locally.

  • tests/unit/ mirrors the package layout one-to-one; the extractor's property test replays the 1,400 captured pages in tests/fixtures/.
  • tests/integration/ runs against a real temporary SQLite file and a live in-process ASGI app — no mocks at the store boundary.
  • Backend line coverage 77% overall: store 91 · queue 88 · pipeline 84 · shared 79 · render 76 · api 62 · cli 41.
  • The frontend has no test harness at all (0%) — treat web/js/ changes as untested until you've clicked through them.
