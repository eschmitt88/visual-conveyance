Slide 3 · core idea

Write down one side, read up the other

scheduler60 s tick→ fetcherHTTP→ extractorHTML → Article→ dedupsimhash→ storeSQLite + FTS
store→ api31 REST endpoints→ web readervanilla JS + cliover HTTP

A one-way ingest pipeline writes into a single SQLite database; a small HTTP API, a vanilla-JS web reader, and a CLI read back out. The store is the hub — everything layers on top of it.

Slide 7 · where you start

Two well-worn hot paths

New source type — a 4-file recipe

  1. pipeline/sources/base.py — subclass SourceAdapter (discover(), fetch_items())
  2. pipeline/sources/__init__.py — register in SOURCE_REGISTRY
  3. store/migrations/ — extend the source_type CHECK constraint
  4. cli/commands/add.py — expose the new --type

Plus a fixture-backed test. All three existing adapters (rss, html_page, mailbox) followed this recipe — see docs/adding-a-source-type.md.

New API endpoint

  • api/routes.py — the handler
  • api/schemas.py — request/response shapes
  • web/js/api.js — only if the frontend consumes it

A new CLI command is even simpler: one module in cli/commands/; main.py auto-discovers it.

A newcomer's first change almost never touches store/ or queue/ — those layers are stable (91% and 88% covered) and change only with schema migrations.

Slide 8 · invariants

Five rules keep it sane

Only store/writer.py writes the database — every INSERT/UPDATE/DELETE lives in that one 610-LOC file.
The extractor is pure — bytes in, Article out; no network, disk, DB, or clock. Deterministic.
The FTS index is trigger-maintained — only SQLite triggers touch articles_fts, so it can never drift.
Queue jobs are idempotent — replays never duplicate articles, which makes retries safe.
The API never fetches inline — "fetch now" enqueues a job and returns 202; only workers touch the network.

These invariants make the pipeline testable and replayable. A property test replays all 1,400 fixture pages on every CI run to enforce extractor purity.

Slide 9 · the complication

Strict layering — with one known crack

api/may import store, render, queue
cli/speaks HTTP via client.py — imports no backend package
pipeline/may import store, queue
the violation
render/may import store
queue/may import store
store/bottom layer — imports nothing but stdlib + sqlite3

allowed imports point downward · nothing imports api/ or cli/

extractor.py line 41 imports clean_html() from render/sanitize.py — there since v0.8. A change to the display sanitizer can silently change what gets stored; two purity tests are xfail. The fix is issue #214.

Slide 11 · also handle with care

Two more places that punish casual edits

api/routes.py — 830 LOC

  • All 31 endpoints in one file
  • 11 routes inline a copy-pasted auth check instead of using auth.py
  • File coverage 54% — below even the module's 62%

web/js/reader.js — 920 LOC

  • Vanilla JS with zero tests
  • Highlights anchor by character offsets into rendered HTML — a markup change in render/template.py silently corrupts them
  • This coupling caused 3 of the last 10 user-reported bugs

Neither is as risky as the extractor, but both reward reading before editing.

Slide 12 · takeaways

What to remember

  1. One-way pipeline into one SQLite file; the store is the hub. ↩ slides 3–4 · deeper: docs/architecture.md
  2. First changes go to pipeline/sources/ (4-file recipe) or api/routes.py — not the store. ↩ slide 7 · deeper: docs/adding-a-source-type.md
  3. Respect the invariants: only writer.py writes, the extractor stays pure, triggers own the FTS index. ↩ slides 8–9
  4. Tread carefully in extractor.py; watch routes.py and reader.js. ↩ slides 10–11
  5. The backend is 77% covered; the frontend has no tests at all. ↩ slide 4
