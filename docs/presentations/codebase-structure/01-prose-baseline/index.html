meridian: a new contributor’s map of the codebase

A self-hosted read-later / RSS service — Python backend, SQLite store, small HTTP API, vanilla-JS reader, CLI.

meridian fetches articles from feeds, pages, and a mail drop; extracts readable text; deduplicates; and stores everything in one SQLite file (~1.8 GB in WAL mode for a typical instance of ~200 feeds and ~120,000 articles). The system is a one-way ingest pipeline — scheduler → fetcher → extractor → dedup → store → full-text index — writing into a single SQLite database that an HTTP API, a web reader, and a CLI all read back out of; your first change will almost certainly land in pipeline/sources/ (new source type) or api/routes.py (new endpoint), and the one file to treat with caution is pipeline/extractor.py. There is no external broker, cache, or database server: one process runs the API, one runs the workers. The store is the hub; everything else layers on top of it.

The shape of the system

The repo is ~23,230 lines total: 13,710 LOC of backend Python under meridian/, a 3,280-line frontend under web/, and 6,240 LOC of tests. The backend splits into six packages plus a small shared layer (config.py and client.py, the HTTP client that both the CLI and tests use):

It talks to the same 31 endpoints as the CLI; neither has a private backdoor into the database.

How data moves

The write path (fetch pipeline)

pipeline/scheduler.py ticks every 60 s, finds feeds whose poll interval (default 30 min) has elapsed, and enqueues one fetch job per feed into a SQLite jobs table. The broker (queue/broker.py) polls that table every 500 ms and leases jobs to 8 worker threads; failures retry with backoff at 1 min / 5 min / 30 min, then dead-letter. Typical queue depth is 30–60 jobs; the health endpoint alerts at 500.

Each job flows through four stages. fetcher.py does the HTTP work (conditional GET via ETag/Last-Modified, 20 s timeout, per-host politeness delay). extractor.py turns raw HTML into a structured Article — title, byline, body, word count — with no I/O of any kind (p50 45 ms, p95 320 ms per article). dedup.py computes a 64-bit simhash of the body (a compact fingerprint of the text); anything within Hamming distance ≤ 3 of a stored hash is flagged as a near-duplicate — about 7% of incoming items are dropped this way. Finally store/writer.py persists each surviving article in a single transaction, and SQLite triggers update the articles_fts FTS5 full-text index — application code never writes the index. End-to-end, p50 from job dequeue to the article being searchable is 2.1 s, dominated by the network fetch.

The read path

GET /articles/{id} hits api/routes.py, which reads via store/reader.py (6 ms p50), assembles display HTML in render/template.py (14 ms), then render/annotations.py merges the user’s highlights — stored as character offsets into the rendered text — into <mark> spans (8 ms). Total p50: 28 ms.

The rules that keep it sane

Five invariants, documented in docs/architecture.md, are what make the pipeline testable and replayable. Break one and you break the codebase’s core discipline:

  1. The extractor is pure. Bytes in → Article out; no network, disk, DB, or clock. The same HTML always yields the same Article, and a property test replays all 1,400 fixture pages on every CI run to enforce it.
  2. Only store/writer.py writes the database. Every INSERT, UPDATE, and DELETE in the codebase lives in that one 610-LOC file; everything else reads through store/reader.py.
  3. The full-text index is trigger-maintained. Only SQLite triggers in schema.sql touch articles_fts, so the index can never drift from the articles table.
  4. Queue jobs are idempotent. Replaying any job must not create duplicate articles — dedup plus the writer’s upsert keys guarantee it, which is what makes the retry policy safe.
  5. The API never fetches inline. “Fetch this now” requests enqueue a job and return 202 Accepted; only workers touch the network.

Import layering is equally strict. store/ sits at the bottom and imports no other meridian package (stdlib and sqlite3 only). queue/ may import store/; pipeline/ may import store/ and queue/; render/ may import store/; api/ may import store/, render/, and queue/. The CLI imports only client.py — it speaks HTTP, never backend packages. And nothing imports api/ or cli/.

The one known layering violation: pipeline/extractor.py (line 41) imports clean_html() from render/sanitize.py — a sideways pipeline → render edge that has existed since v0.8. A change to the display sanitizer can silently change what gets stored, and two extractor purity tests are marked xfail because of it. The fix (moving clean_html() to a shared location) is tracked as issue #214, the top item on the architecture debt list.

The one scary file — and two lesser hotspots

pipeline/extractor.py is the largest file in the repo at 1,140 LOC. It carries 14 site-specific extraction heuristics inlined as if/elif chains, with a maximum cyclomatic complexity of 38 (roughly: one function has 38 independent paths through it), plus the layering violation above. Nearly every extraction bug fix lands here, and each one risks changing output for the other 13 heuristics. The 1,400-page fixture corpus is the only safety net. Tread carefully.

api/routes.py holds all 31 endpoint handlers in one 830-LOC file. auth.py exists, but 11 routes inline their own copy-pasted auth check instead of using it, and file-level coverage is 54% — below even the api module’s 62%.

web/js/reader.js is 920 LOC of vanilla JS with zero tests. Highlight anchoring uses character offsets into the rendered HTML, so any markup change in render/template.py silently corrupts existing highlight positions — a coupling behind 3 of the last 10 user-reported bugs.

Where your first change goes

Adding a new source type is the most common contribution, and it’s a known 4-file recipe (spelled out in docs/adding-a-source-type.md):

  1. pipeline/sources/base.py — subclass SourceAdapter, implementing discover() and fetch_items().
  2. pipeline/sources/__init__.py — register the class in SOURCE_REGISTRY.
  3. store/migrations/ — one migration extending the source_type CHECK constraint.
  4. cli/commands/add.py — expose the new --type value.

Plus a fixture-backed test under tests/unit/pipeline/. The three existing adapters — RSS/Atom, single-page save, and newsletter-by-IMAP — each followed exactly this recipe.

Adding an API endpoint touches api/routes.py and api/schemas.py, plus web/js/api.js if the frontend consumes it. Adding a CLI command is a single new module in cli/commands/ — main.py auto-discovers it.

A newcomer’s first change almost never touches store/ or queue/. Those layers are stable (91% and 88% covered) and change only with schema migrations.

What the tests do — and don’t — cover

412 tests total (348 unit + 64 integration), running in ~41 s locally. tests/unit/ mirrors the package layout one-to-one; the extractor’s property test replays the 1,400 captured HTML pages in tests/fixtures/. Integration tests run against a real temporary SQLite file and a live in-process ASGI app — no mocks at the store boundary. Backend line coverage is 77% overall, but it is uneven: store 91%, queue 88%, pipeline 84%, shared 79%, render 76%, api 62%, cli 41%.

The frontend has no automated tests at all — 0%, with no JS test harness in the repo. Any change under web/, and especially to reader.js, is verified only by hand.

In short

Learn the write path once and the codebase falls into place: everything either feeds the SQLite store or reads from it, under strict layering with store/ at the bottom. Make your first change in pipeline/sources/ or api/routes.py, respect the five invariants, and treat pipeline/extractor.py — and anything touching highlight offsets in the untested frontend — with respect.
