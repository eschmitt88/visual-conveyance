meridian: a one-way pipeline in, one SQLite file in the middle, everything reads back out

meridian is a self-hosted read-later / RSS service: a Python backend (an ingest pipeline feeding a SQLite store), a small HTTP API, a vanilla-JS web reader, and a CLI. One process runs the API, one runs the workers — no external broker, cache, or database server. The store is the hub; everything layers on top of it.

Inspector

pipeline/scheduler.py · 310 LOC

scheduler — decides what to fetch, and when

  • Ticks every 60 s; finds feeds whose poll interval (default 30 min) has elapsed and enqueues one fetch job per feed.
  • Typical queue depth is 30–60 jobs; the health endpoint alerts at 500.

meridian/queue/ · 1,120 LOC · 88% coverage

queue — a job queue on a SQLite table

  • No Redis, no Celery, no external broker — jobs live in a SQLite table.
  • broker.py (460 LOC) polls the jobs table every 500 ms, leases jobs, acks. worker.py (430 LOC) runs a pool of 8 threads by default.
  • retry.py (230 LOC): exponential backoff at 1 min / 5 min / 30 min, then dead-letter.
  • Jobs are idempotent: replaying any job never creates duplicate articles (dedup + the writer’s upsert keys) — that is what makes the retry policy safe.

pipeline/fetcher.py · 620 LOC

fetcher — all the HTTP work

  • Conditional GET (ETag / Last-Modified), 20 s timeout, per-host politeness delay.
  • The network fetch dominates write-path latency: end-to-end p50 from dequeue to searchable is 2.1 s.

pipeline/extractor.py · 1,140 LOC — the largest file in the repo

extractor — the scary one. Tread carefully.

  • Raw HTML → structured Article (title, byline, body, word count). Pure: no network, disk, DB, or clock; deterministic. p50 45 ms, p95 320 ms per article.
  • 14 site-specific extraction heuristics inlined as if/elif chains (max cyclomatic complexity 38). Nearly every extraction bug fix lands here, and each one risks changing output for the other 13.
  • The layering violation: line 41 imports clean_html() from render/sanitize.py (since v0.8). A change to the display sanitizer can silently change what gets stored; two purity tests are marked xfail because of it. The fix (moving clean_html() to a shared location) is issue #214, top of the debt list.
  • The only safety net: a property test replays all 1,400 fixture pages on every CI run.

pipeline/dedup.py · 380 LOC

dedup — near-duplicate detection

  • Computes a 64-bit simhash of the body; Hamming distance ≤ 3 against stored hashes marks a duplicate.
  • About 7% of incoming items are flagged and dropped.

pipeline/sources/ · registry pattern

sources — adapters, one per source type

  • base.py (190 LOC): SourceAdapter ABC — subclass to add a type. __init__.py (140 LOC): SOURCE_REGISTRY maps type → adapter.
  • Adapters: rss.py (410), html_page.py (520, single-page “save this URL”), mailbox.py (470, newsletter-by-email via IMAP).
  • The center of the 4-file recipe for the most common contribution — see “Your first change” below.

meridian/store/ · 2,310 LOC · 91% coverage

store — the hub; the only module that touches SQLite

  • Bottom layer: imports no other meridian package (stdlib + sqlite3 only).
  • writer.py (610 LOC): every INSERT/UPDATE/DELETE in the codebase lives in this one file. Each surviving article is persisted in a single transaction.
  • reader.py (720 LOC): all read queries; returns frozen dataclasses (6 ms p50 in the read path).
  • schema.sql (280 LOC): 9 tables + articles_fts (FTS5) + the triggers that maintain it — application code never writes the index. migrations/: 7 numbered scripts. db.py (340 LOC): connections, WAL mode, pragmas.
  • Stable and well-covered — a newcomer’s first change almost never lands here; it changes only with schema migrations.

meridian/render/ · 1,610 LOC · 76% coverage

render — stored article → display HTML

  • template.py (520 LOC): article HTML assembly, typography (14 ms in the read path).
  • sanitize.py (480 LOC): clean_html(), tag allowlist — also imported, against the rules, by the extractor.
  • annotations.py (610 LOC): merges the user’s highlights — stored as character offsets into the rendered text — into <mark> spans (8 ms).

meridian/api/ · 2,940 LOC · 62% coverage

api — the HTTP surface

  • ASGI app; all 31 endpoint handlers in one file, routes.py (830 LOC) — a hotspot; its file-level coverage is 54%, below even the module’s 62%.
  • 11 routes inline a copy-pasted auth check instead of using auth.py (310 LOC, token auth, single-user).
  • Never fetches inline: “fetch this now” enqueues a job and returns 202 Accepted; only workers touch the network.
  • schemas.py (690, request/response dataclasses + validation), pagination.py (280, cursor pagination), opml.py (470, feed-list import/export), errors.py (120), app.py (240).
  • Read path GET /articles/{id}: reader 6 ms + template 14 ms + annotations 8 ms = p50 28 ms.

web/ · 3,280 lines · no automated tests (0%)

web — the vanilla-JS reader. Untested.

  • No framework, no build step: 2,760 LOC JS + 380 CSS + 140 HTML. There is no JS test harness at all.
  • reader.js (920 LOC, hotspot): highlight anchoring uses character offsets into the rendered HTML, so any markup change in render/template.py silently corrupts existing highlight positions. This coupling caused 3 of the last 10 user-reported bugs.
  • app.js (430, boot + routing), api.js (310, one fetch() wrapper per endpoint used), list.js (640, list/filters/keyboard nav), settings.js (460, feeds + OPML upload).
  • Consumes the same endpoints as the CLI — no private backdoor into the database.

meridian/cli/ · 980 LOC · 41% coverage

cli — a client, not a backend

  • Talks to the API over HTTP via the shared client.py (330 LOC); imports no backend package.
  • main.py (160 LOC) auto-discovers commands/: add (180), sync (200), search (220), export (220).
  • Adding a command is one new module in cli/commands/.

Your first change — the two (and a half) hot paths

A newcomer’s first change almost never touches store/ or queue/ — those layers are stable (91% and 88% covered) and change only with schema migrations.

The 4-file recipe (per docs/adding-a-source-type.md)

  1. meridian/pipeline/sources/base.py — subclass SourceAdapter; implement discover() and fetch_items().
  2. meridian/pipeline/sources/__init__.py — register the class in SOURCE_REGISTRY.
  3. meridian/store/migrations/ — one migration extending the source_type CHECK constraint.
  4. meridian/cli/commands/add.py — expose the new --type value.

Plus a fixture-backed test under tests/unit/pipeline/. All three existing adapters (rss.py, html_page.py, mailbox.py) followed this recipe.

Two files, sometimes three

  1. meridian/api/routes.py — the handler (all 31 live in this one 830-LOC file).
  2. meridian/api/schemas.py — request/response dataclasses + validation.
  3. web/js/api.js — only if the frontend consumes the new endpoint.

Caution: routes.py is a debt hotspot — 11 routes inline a copy-pasted auth check; use auth.py instead. File-level coverage there is 54%.

One file

  1. One new module in meridian/cli/commands/ — main.py auto-discovers it.

The CLI speaks HTTP through client.py; it never imports backend packages.

The rules that keep it sane

Five load-bearing invariants

  • The extractor is pure. Bytes in → Article out; no network, disk, DB, or clock. Deterministic. A property test replays all 1,400 fixture pages on every CI run.
  • Only store/writer.py writes the database. Every INSERT/UPDATE/DELETE in the codebase lives in that one 610-LOC file; everything else reads through store/reader.py.
  • The FTS index is trigger-maintained. articles_fts is updated only by SQLite triggers in schema.sql — no Python touches it, so it can never drift from the articles table.
  • Queue jobs are idempotent. Replaying any job must not create duplicate articles (dedup + upsert keys) — this is what makes retries safe.
  • The API never fetches inline. “Fetch this now” enqueues a job and returns 202 Accepted; only workers touch the network.

These are what make the pipeline testable and replayable. Break one and you break the codebase’s core discipline.

Import layering (from docs/architecture.md)

  • store/ is the bottom: imports no other meridian package (stdlib + sqlite3 only).
  • queue/ may import store/.
  • pipeline/ may import store/ and queue/.
  • render/ may import store/.
  • api/ may import store/, render/, queue/.
  • cli/ imports only client.py — it speaks HTTP, never backend packages.
  • Nothing imports api/ or cli/.
  • The one known violation: pipeline/extractor.py:41 imports clean_html() from render/sanitize.py — a sideways pipeline → render edge, in place since v0.8. Display-sanitizer changes can silently change what gets stored; two extractor purity tests are xfail. Fix tracked as issue #214, top of the debt list.

Tests

  • tests/unit/ mirrors the package layout one-to-one; the extractor’s property test replays the 1,400 captured HTML pages in tests/fixtures/.
