meridian, drawn as a transit network — two lines, one hub

meridian is a self-hosted read-later / RSS service: one Python backend (13,710 LOC), one worker process and one API process, and one SQLite file (typically 1.8 GB, ~120,000 articles from ~200 feeds) — no external broker, cache, or database server. Below, the whole codebase as a transit map: every station is a real file, the two lines are its two data paths, and the zones are its import layers.

How to rideReading this map

The metaphor is literal where it counts. Stations are files (with LOC where it matters), lines are data flows, and zones are import layers — the deeper the zone, the fewer things that layer is allowed to depend on. The hub is the single SQLite file in WAL mode (a journal mode that lets readers keep reading while a write is in progress). Two lines only: the blue Ingest Line carries content one-way from the outside world into the hub; the green Reader Loop carries it back out to you. One process runs the API, one runs the workers; the queue is a SQLite table, so there is no Redis, no Celery, no external anything. The backend is Python 3.12 with 11 runtime dependencies, managed by uv.

Line 1 · blue · one-wayThe Ingest Line — from the outside world to the hub

End to end, an article takes p50 2.1 s from job dequeue to being searchable — dominated by the network fetch. Station by station:

  1. scheduler.py (310 LOC) ticks every 60 s, finds feeds whose poll interval (default 30 min) has elapsed, and enqueues one fetch job per feed. Typical queue depth is 30–60 jobs; the health endpoint alerts at 500.
  2. queue/broker.py (460 LOC) polls the jobs table every 500 ms and leases jobs to worker.py’s 8 threads (default). Failures retry with backoff at 1 min / 5 min / 30 min (retry.py), then move to the dead-letter siding (parked permanently; no further retries).
  3. fetcher.py (620 LOC) does the HTTP work: conditional GET (ETag/Last-Modified — only re-download what changed), a 20 s timeout, and a per-host politeness delay. Which adapter handles the source comes from SOURCE_REGISTRY in pipeline/sources/: RSS/Atom feeds (rss.py, 410 LOC), single saved pages (html_page.py, 520 LOC), or newsletter-by-email via IMAP (mailbox.py, 470 LOC) — all subclasses of the SourceAdapter base class.
  4. extractor.py (1,140 LOC) turns raw HTML into a structured Article — title, byline, body, word count. It is pure: no network, no disk, no DB, no clock; the same HTML always yields the same Article. p50 45 ms, p95 320 ms per article. (Also the map’s scariest station — see “stations under repair”.)
  5. dedup.py (380 LOC) computes a 64-bit simhash of the body (a fingerprint where similar texts get similar bits); Hamming distance ≤ 3 against stored hashes marks a duplicate. About 7% of incoming items are flagged and dropped.
  6. store/writer.py (610 LOC) persists each surviving article in a single transaction. SQLite triggers defined in schema.sql then update the articles_fts full-text index (FTS5 — SQLite’s built-in full-text search) — application code never writes the index.

Line 2 · greenThe Reader Loop — from the hub back to you

GET /articles/{id} makes the full loop in p50 28 ms:

  1. api/routes.py receives the request — all 31 REST endpoints live in this one file. The API layer also carries token auth (single-user, auth.py), cursor pagination (pagination.py), OPML import/export of feed lists (opml.py), and request/response schemas (schemas.py), assembled into an ASGI app (async Python web-server interface) in app.py.
  2. store/reader.py (720 LOC) fetches the stored article — 6 ms p50, returning frozen dataclasses.
  3. render/template.py assembles the display HTML — 14 ms.
  4. render/annotations.py merges your highlights — stored as character offsets into the rendered text — into <mark> spans: 8 ms.

The web reader (web/js/reader.js) and the CLI ride the same loop: both consume the same endpoints, and neither has a private backdoor into the database. The CLI speaks HTTP through the shared client.py and imports no backend package. And the API never fetches inline: a “fetch this now” request just enqueues a job and returns 202 Accepted — only workers touch the network.

ZonesZone regulations — who may import whom

The layering is strict, documented in docs/architecture.md, and each package has an explicit allowlist:

  • store/ — imports no other meridian package (stdlib + sqlite3 only). It owns the schema (9 tables + articles_fts), the 7 numbered migrations, and the WAL/pragma setup.
  • queue/ — may import store/.
  • render/ — may import store/.
  • pipeline/ — may import store/ and queue/.
  • api/ — may import store/, render/, and queue/.
  • cli/ — imports only client.py; it speaks HTTP and never imports backend packages.
  • Nothing imports api/ or cli/.

The one unofficial track

pipeline/extractor.py (line 41) imports clean_html() from meridian/render/sanitize.py — a sideways pipeline → render edge that has existed since v0.8 and is drawn dashed red on the map. It means a change to the display sanitizer can silently change what gets stored, and it is why two extractor purity tests are marked xfail (expected to fail). The fix — moving clean_html() down into a shared location — is tracked as issue #214 and is the top item in docs/architecture.md’s debt list.

Track regulationsThe five invariants that keep the network sane

  • The extractor is pure. Bytes in → Article out; no network, disk, DB, or clock, and deterministic. A property test replays all 1,400 fixture pages on every CI run to enforce it.
  • Only store/writer.py writes the database. Every INSERT, UPDATE, and DELETE in the codebase lives in that one 610-LOC file; everything else reads through store/reader.py.
  • The FTS index is trigger-maintained. articles_fts is updated only by SQLite triggers in schema.sql; no Python code ever touches it, so it can never drift from the articles table.
  • Queue jobs are idempotent (safe to run twice). Replaying any job must not create duplicate articles — dedup plus the writer’s upsert keys guarantee it, which is what makes the retry policy safe.
  • The API never fetches inline. “Fetch this now” enqueues a job and returns 202 Accepted; only workers touch the network.

Break one of these and you break the property that makes the pipeline testable and replayable.

CautionStations under repair — the three tech-debt hotspots

Hotspot 1 — the scary one

pipeline/extractor.py

1,140 LOC, the largest file in the repo. 14 site-specific extraction heuristics inlined as if/elif chains, max cyclomatic complexity 38 (count of independent paths through the code) — plus the layering violation above.

Nearly every extraction bug fix lands here, and each one risks changing output for the other 13 heuristics. The 1,400-page fixture corpus is the only safety net. Tread carefully.

Hotspot 2

api/routes.py

All 31 endpoints in one 830-LOC file. auth.py exists, but 11 routes inline their own copy-pasted auth check instead of using it.

File-level coverage is 54% — below even the api module’s 62%.

Hotspot 3

web/js/reader.js

920 LOC of vanilla JS with zero tests. Highlight anchoring uses character offsets into the rendered HTML, so any markup change in render/template.py silently corrupts existing highlight positions.

This coupling has caused 3 of the last 10 user-reported bugs.

First journeyWhere a new contributor boards

Your first change almost certainly lands at one of the two ★ stations — and almost never in store/ or queue/, which are stable (91% and 88% covered) and change only with schema migrations.

★ Most common — new source type

The 4-file recipe

Per docs/adding-a-source-type.md, exactly four files:

1. pipeline/sources/base.py — subclass SourceAdapter (implement discover() and fetch_items())
2. pipeline/sources/__init__.py — register it in SOURCE_REGISTRY
3. store/migrations/ — one migration extending the source_type CHECK constraint
4. cli/commands/add.py — expose the new --type value

Plus a fixture-backed test under tests/unit/pipeline/. All three existing adapters followed this exact recipe.

★ New API endpoint

Two files, maybe three

api/routes.py + api/schemas.py, and web/js/api.js if the frontend consumes it.

New CLI command

One file

One new module in cli/commands/ — main.py auto-discovers it.

Honesty checkWhere the map would mislead you

  • Zones oversell “downhill”. The bands suggest any module may import anything below it. The real rule is a per-package allowlist: pipeline/ may not import render/ even though render sits in a deeper zone — which is exactly why the red extractor→sanitize track is a violation and not just a shortcut.
  • Passengers don’t survive the ride. On a real transit line the same rider exits who boarded. On the Ingest Line, each station transforms its cargo: raw HTML boards at the fetcher and a different thing — a structured Article — arrives at the hub. Stations manufacture; they don’t just stop.
  • One station has no train service at all. articles_fts is reached only by trackside machinery — SQLite triggers. No code ever “rides” there, and treating it as a normal writable station (writing to the index from Python) would break invariant #3.
