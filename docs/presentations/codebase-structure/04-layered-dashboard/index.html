meridian · codebase structure — for your first contribution

A one-way ingest pipeline writes into a single SQLite file; a small HTTP API, a vanilla-JS reader, and a CLI read it back out. The store is the hub — everything layers on top of it.

Self-hosted read-later / RSS service. Two processes — one API, one set of workers — with no external broker, cache, or database server. A typical instance tracks ~200 feeds and holds ~120,000 articles in one 1.8 GB SQLite file (WAL mode).

⇢ Write path — the fetch pipeline

scheduler → jobs table → fetcher → extractor → dedup → store → FTS index. Articles flow one way into the store. About ≈7% of incoming items are flagged as near-duplicates and dropped; application code never writes the search index.

2.1 s  p50 from job dequeue to the article being searchable — dominated by the network fetch

Full detail — the six stages, with numbers
  1. pipeline/scheduler.py ticks every 60 s, finds feeds whose poll interval (default 30 min) has elapsed, and enqueues one fetch job per feed. Typical queue depth is 30–60 jobs; the health endpoint alerts at 500.
  2. queue/broker.py polls the jobs table every 500 ms and leases jobs to 8 worker threads (queue/worker.py). Failures retry with backoff at 1 min / 5 min / 30 min (queue/retry.py), then dead-letter.
  3. pipeline/fetcher.py does the HTTP work: conditional GET (ETag/Last-Modified), 20 s timeout, per-host politeness delay.
  4. pipeline/extractor.py turns raw HTML into a structured Article (title, byline, body, word count). It is pure — p50 45 ms, p95 320 ms per article, no I/O of any kind.
  5. pipeline/dedup.py computes a 64-bit simhash of the body; Hamming distance ≤ 3 against stored hashes marks a duplicate. About 7% of incoming items are flagged and dropped.
  6. store/writer.py persists each surviving article in a single transaction. SQLite triggers defined in schema.sql update the articles_fts FTS5 index — application code never writes the index.

⇠ Read path — serving an article

browser / CLI → api → store/reader → render → response. The web reader (web/js/reader.js) and the CLI consume the same endpoints — neither has a private backdoor into the database.

28 ms  p50 for GET /articles/{id}, end to end

Full detail — the 28 ms budget

GET /articles/{id} hits api/routes.py, which:

  1. reads the stored article via store/reader.py — 6 ms p50 (reads return frozen dataclasses);
  2. assembles display HTML in render/template.py — 14 ms;
  3. merges the user's highlights in render/annotations.py — stored as character offsets into the rendered text — into <mark> spans — 8 ms.

Total p50 28 ms. The character-offset scheme is also the frontend's fragile coupling — see Hotspots.

≣ Import layering — and its one violation

store/ is the bottom layer and nothing imports api/ or cli/. The layering is strict and documented in docs/architecture.md — with exactly one known violation, in the extractor.

⚠ The violation: pipeline/extractor.py (line 41) imports clean_html() from render/sanitize.py — a sideways pipeline → render edge, present since v0.8.
Full detail — the rules and why the violation matters
  • store/ imports no other meridian package (stdlib + sqlite3 only).
  • queue/ may import store/.
  • pipeline/ may import store/ and queue/.
  • render/ may import store/.
  • api/ may import store/, render/, and queue/.
  • cli/ imports only client.py — it speaks HTTP and never imports backend packages.
  • Nothing imports api/ or cli/.

The violation means a change to the display sanitizer can silently change what gets stored, and it is the reason two extractor purity tests are marked xfail. The fix — moving clean_html() down into a shared location — is tracked as issue #214 and is the top item in docs/architecture.md's debt list.

✓ The five load-bearing invariants

Pure extractor · single writer · trigger-maintained FTS · idempotent jobs · no inline fetches in the API. These are what make the pipeline testable and replayable — break one and you break the codebase's core discipline.

Full detail — each rule and what enforces it
  1. The extractor is pure. Bytes in → Article out. No network, no disk, no DB, no clock. Deterministic: the same HTML always yields the same Article. A property test replays all 1,400 fixture pages on every CI run to enforce this.
  2. Only store/writer.py writes the database. Every INSERT, UPDATE, and DELETE in the codebase lives in that one 610-LOC file. Everything else reads through store/reader.py.
  3. The FTS index is trigger-maintained. articles_fts is updated only by SQLite triggers in schema.sql; no Python code ever touches it directly, so the index can never drift from the articles table.
  4. Queue jobs are idempotent. Replaying any job must not create duplicate articles — dedup plus the writer's upsert keys guarantee it, which is what makes the retry policy safe.
  5. The API never fetches inline. "Fetch this now" requests enqueue a job and return 202 Accepted; only workers touch the network.

⚑ Tech-debt hotspots — where to tread carefully

Three files demand caution: pipeline/extractor.py (the scary one), api/routes.py, and web/js/reader.js.

⚠ The scary one: extractor.py — 1,140 LOC, the largest file in the repo. Nearly every extraction bug fix lands here, and each one risks changing output for the other 13 heuristics.
Full detail — all three hotspots
  1. meridian/pipeline/extractor.py. 1,140 LOC, the largest file in the repo. Contains 14 site-specific extraction heuristics inlined as if/elif chains (max cyclomatic complexity 38), plus the layering violation (see Layering). Nearly every extraction bug fix lands here, and each one risks changing output for the other 13 heuristics. The 1,400-page fixture corpus is the only safety net.
  2. meridian/api/routes.py. All 31 endpoints in one 830-LOC file. auth.py exists, but 11 routes inline their own copy-pasted auth check instead of using it. File-level coverage is 54% — below even the module's 62%.
  3. web/js/reader.js. 920 LOC of vanilla JS with zero tests. Highlight anchoring uses character offsets into the rendered HTML, so any markup change in render/template.py silently corrupts existing highlight positions. This coupling has caused 3 of the last 10 user-reported bugs.

▶ Your first change — the two hot paths

Adding a source type (the most common contribution) is a known 4-file recipe; adding an API endpoint centers on api/routes.py. A newcomer's first change almost never touches store/ or queue/ — those layers are stable (91% and 88% covered) and change only with schema migrations.

Full detail — the recipes, file by file

Adding a new source type touches exactly 4 files, per docs/adding-a-source-type.md:

  1. meridian/pipeline/sources/base.py — subclass SourceAdapter (implement discover() and fetch_items()).
  2. meridian/pipeline/sources/__init__.py — register the class in SOURCE_REGISTRY.
  3. meridian/store/migrations/ — one migration extending the source_type CHECK constraint.
  4. meridian/cli/commands/add.py — expose the new --type value.

Plus a fixture-backed test under tests/unit/pipeline/. The three existing adapters (rss.py, html_page.py, mailbox.py) each followed this recipe.

Adding an API endpoint touches api/routes.py + api/schemas.py, and web/js/api.js if the frontend consumes it.

Adding a CLI command is one new module in cli/commands/ — main.py auto-discovers it.
